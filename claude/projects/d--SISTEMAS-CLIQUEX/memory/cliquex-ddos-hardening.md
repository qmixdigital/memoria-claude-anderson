Em 2026-07-25 a rede sofreu um **flood HTTP** (~1.680 req/s, botnet com UAs/IPs rotativos: `curl/8.7.1`, `SemrushBot`, `Baiduspider`, `Chrome/150` falso, IPs `185.177.72.49/22`, `143.198.205.54`). Sintoma: `cliquex.click` e os sites lentíssimos (TTFB 9–27s), Cloudflare devolvendo **522/525** (origem inalcançável).

**Causas-raiz no VPS** (`ssh cliquex`, 2 vCPU / 2,9 GB): (1) `worker_connections 768` (default Debian) — estourou com 2000+ conexões → workers do Nginx sem file descriptor (`socket() failed (24: Too many open files)`) e mortos por OOM (`signal 9`), derrubando o listener `:443`; (2) **sem `ssl_session_cache`** → todo request refazia handshake TLS completo (CPU); (3) **VPS é container** → NÃO deixa criar swap (`swapon: Operation not permitted`), então OOM mata direto; (4) **`cliquex.click` estava fora do Cloudflare** (DNS-only, IP da origem exposto direto, zero proteção) — apanhava direto além do colateral do box compartilhado.

**Hardening aplicado** (fica no `/etc/nginx/nginx.conf`, backup `.bak-perf`): `worker_connections` (ver ajuste abaixo), `worker_rlimit_nofile 65535`, `multi_accept on`, `ssl_session_cache shared:SSL:50m` + `ssl_session_tickets on` + `ssl_session_timeout 1d`. Depois de aplicar precisou **`systemctl restart nginx`** (reload não recria sockets mortos). Scripts: `scratchpad/fix_nginx.py`.

**CUIDADO — OOM (2026-07-25 13:30)**: subi `worker_connections` pra 8192 durante o flood, mas nesse box de **2,9GB sem swap** isso deixou o nginx crescer até 2,3G (buffers TLS por conexão) e o **OOM killer matou o nginx** (derrubou TODOS os sites; `systemctl start nginx` ressuscita). **Corrigido para `worker_connections 3072`** (memória segura, ainda cobre tráfego normal do CF). NÃO voltar pra 8192 nesse box — se houver flood, quem segura é o Cloudflare (Under Attack/WAF), não aumentar worker_connections. Sintoma do OOM: `systemctl reload` diz "Unit cannot be reloaded because it is inactive" e curl dá HTTP 000.

**INCIDENTE OOM no servidor NOVO + blindagem definitiva (2026-07-26 ~14h)**: mesmo no Hetzner cx33 (8GB) o **nginx sofreu OOM** (cresceu a 1,7GB sob pico de conexões, `worker_connections 8192`) → kernel matou o nginx → `:443` morto → **Cloudflare 521** no `/clk` e `/api`. **O rodízio NÃO caiu** (Worker no edge serve `/` e `/whatsapp-*`; cliques ficaram no buffer do DO, nada perdido) — só a origem (painel + sync) ficou fora ~20min. Causa das conexões: pico via IPs CF (as conexões eram ociosas/lentas, poucos requests no log — quase todo o access log da origem é o próprio DO a cada 30s, o que é normal). **Defesa em profundidade aplicada (a origem nunca mais deve ficar fora):** (1) **SWAP 4GB** — a VM é **KVM** (`systemd-detect-virt`=kvm), permite swap (o box antigo era container e não deixava); `vm.swappiness=10` (só emergência), fstab persistente → rede de segurança anti-OOM; (2) **`worker_connections` 8192→3072** (teto de memória seguro; sob flood recusa excesso em vez de morrer); (3) **`keepalive_timeout 20s` + `reset_timedout_connection on`** (libera conexões ociosas/slowloris); (4) **nginx auto-restart**: `/etc/systemd/system/nginx.service.d/override.conf` com `Restart=always`, `RestartSec=2`, `OOMScoreAdjust=-800` (kernel mata outra coisa antes do nginx master); (5) **watchdog** `/usr/local/bin/cliquex-watchdog.sh` (cron 1min, `/etc/cron.d/cliquex-watchdog`) — curl no `/health` local e reinicia nginx se travar; **CUIDADO: usar UA de navegador no watchdog** (o vhost tem `if ($is_bot) return 444` que barra `curl` → 000 → reinício em loop falso); (6) **Rate-limit CF na zona cliquex.click** (phase http_ratelimit): `>200 req/10s por IP → block`, expressão **exclui o rodízio** `(path ne "/" and not starts_with(path,"/whatsapp-"))` — protege /clk,/api,/wp-admin,scans sem NUNCA tocar o lead; o DO (4/min) passa folgado. Regra de ouro mantida (rate-limit não pega / nem /whatsapp-*). Ver [[cliquex-worker-rotador]] e [[cliquex-deploy]].

**ATAQUE SLOWLORIS + loop de watchdog (2026-07-26 ~12h, servidor novo)**: sintoma = origem oscilando (`/health` 000 intermitente), nginx `worker process exited on signal 9`, `nginx.service: Failed with result 'timeout'`. DUAS causas somadas: (1) **watchdog agressivo demais** — rodava a cada 1min e reiniciava o nginx a cada 2 falhas; como o `systemctl restart` do nginx demora ~5s (espera conexões keepalive da CF fecharem), cada restart criava janela de 000 que o próprio watchdog pegava → **loop de restart**. Fix: (a) override nginx `TimeoutStopSec=5` + `KillMode=mixed` (mata rápido, não trava no stop); (b) watchdog reescrito CONSERVADOR — roda a cada 5min, exige **3 falhas seguidas**, `curl --max-time 10`, e **cooldown de 15min** (`/var/run/cliquex-wd-cooldown`, checa `stat -c %Y`) pra nunca loopar; o infra-alert também faz 3 tentativas antes de alertar. (2) **Ataque slowloris real**: **5885 conexões estabelecidas na :443 mas só ~6 requests/min** (assinatura de conexões lentas/ociosas) do range **185.177.72.0/22** (mesmo atacante histórico), passando pela CF → esgotava o nginx sem aparecer no access log. Fix: **WAF block no Cloudflare** `(ip.src in {185.177.72.0/22})` (phase `http_request_firewall_custom`, ruleset `95b80c0e...` na zona cliquex.click) + `systemctl restart nginx` 1x pra limpar as conexões velhas → conexões 5885→235, `/health` 15/15 em 200. DIAGNÓSTICO-CHAVE: `ss -tn state established | grep -c :443` (nº conexões) vs requests/min no access log — se conexões >> requests, é slowloris (não flood de requests, então rate-limit por request não pega; precisa WAF block por IP). O rodízio (edge) ficou intacto o tempo todo. Ver [[cliquex-alertas-telegram]].

**AUTO-DEFESA ATIVA (2026-07-26, servidor novo)**: até então a defesa era só resiliência (leads no edge nunca param) + bloqueio MANUAL do atacante. Agora há **bloqueio automático**: `/usr/local/bin/cliquex-autodefesa` (cron `/etc/cron.d/cliquex-autodefesa`, a cada 2min) lê o access log (IP real via real_ip/CF-Connecting-IP), conta requests por IP nos últimos 2min IGNORANDO o próprio DO (`grep -v CliquexEdge|/api/rotator-|/health`), e se algum IP passa **150 req/2min** bloqueia na **borda da Cloudflare** via IP Access Rules API (`POST /zones/{Z}/firewall/access_rules/rules`, mode=block), notifica Telegram (🚫) e registra em `/var/lib/cliquex/blocked/<ip>` (persiste reboot). `cliquex-autodefesa-limpa` (cron diário 04:00) **desbloqueia após 48h** (DELETE na API). Se conexões :443 > 3000 mas nenhum IP domina (slowloris puro) → alerta Telegram p/ ação manual. Config/token em **`/root/.cliquex-cf`** (`CF_TOKEN`=cfat_ da conta26/Endrick + `CF_ZONE`). Whitelist: `/root/.cliquex-whitelist`. Ajuste sem editar script via env: `CLX_THRESHOLD`, `CLX_WINDOW`, `CLX_DRYRUN=1` (testa sem bloquear), `CLX_LOG`. **FIX 2026-07-30 — whitelist por PREFIXO**: o dono foi auto-banido 2x (Error 1106) porque a checagem era `grep -qxF` (IP EXATO) e o IPv6 dele **roda o sufixo dentro do `/64`** (`2804:3d90:82bc:dd20:...`). Corrigido: a whitelist agora casa por **prefixo** (`case "$IP" in "$_w"*)`), e cadastrei o prefixo `2804:3d90:82bc:dd20:` (com `:` final). Também criei **IP Access Rule `allow` do `/64`** na zona cliquex.click (allow vence block na CF, blindagem dupla). Ao whitelistar IPv6 do dono: usar sempre o **prefixo /64 com `:` no fim**, nunca o IP completo. Backup do script: `.bak-wl`. Testado end-to-end com IP 192.0.2.66 (TEST-NET): detectou→bloqueou→notificou→expirou. NUNCA toca o rodízio (só conta/bloqueia paths de origem; leads no edge intactos). Ver [[cliquex-alertas-telegram]].

**AUTOMAÇÃO anti-flood (2026-07-26)**: servidor migrado pra Hetzner cx33 (ver [[cliquex-deploy]]). Defesas automáticas que dispensam firefighting manual: (1) **Firewall Hetzner** — :443/:80 só de IPs Cloudflare (flood DIRETO no IP morre na borda da rede); (2) **Nginx real_ip** do CF (logs mostram IP real do atacante — foi assim que se achou o alvo jornalcidademg com 2M requests); (3) **Cloudflare Rate Limiting rule** nos 29 estáticos: `>200 req/10s por IP → block` (phase `http_ratelimit`; free só permite `period=10`, `mitigation_timeout=10`, action `block`, characteristics `["ip.src","cf.colo.id"]`). Bloqueia flood por-IP sozinho na borda; humano/CGNAT/Googlebot não chegam nesse rate. **NO ROTADOR cliquex.click NÃO tem rate-limit** (regra de ouro: lead nunca bloqueado). Limitação: flood MUITO distribuído (milhares de IPs a <200/10s cada) fura o per-IP → fallback = Under Attack na zona específica (nunca no rotador). O nginx per-vhost limit_req foi tentado mas é frágil (symlink dá "duplicate") — preferir a regra no Cloudflare.

**Flood persistente atinge o ROTADOR também (2026-07-25 noite)**: o flood voltou mirando `cliquex.click` (via CF; logs: referrers `rblc.com.br`/`mareonline.com.br`, paths `/whatsapp-*`). O app Node (2 instâncias) não aguenta → `upstream timed out`/`no live upstreams` → 502/521/522, e o Nginx **OOM de novo** (2.3G). O flood chega TODO via IPs Cloudflare (162.158.x/172.70.x/104.23.x) — não é direto na origem; ou seja passa pelas configs leves. Managed_challenge/SBFM/security medium NÃO seguraram (5313 conexões). Só **Under Attack** segura. AÇÃO tomada: Under Attack em TODOS os 21 (20 estáticos + rotador) → conexões 5313→5, box recuperou. Trade-off: rotador fica com desafio de ~5s antes do redirect (não é o "rápido/sem interferência" ideal, mas fica NO AR). **FIX DEFINITIVO do rotador = Cloudflare Worker** fazendo o 302 no edge (flood nunca chega na origem fraca, sem desafio, instantâneo) — **FEITO em 2026-07-26, ver [[cliquex-worker-rotador]]**. Agora `/` e `/whatsapp-*` respondem no edge; flood na origem não derruba mais o lead. O box (2 vCPU/2,9GB/sem swap) é pequeno demais pra aguentar flood que fura o CF.

**Sobre o alvo (atualizado 2026-07-25)**: o flood é INTERMITENTE e atinge TAMBÉM os 20 estáticos, não só o rotador. Numa janela testei relaxar os estáticos p/ `medium` e ficou estável (44–90 conexões) — mas horas depois o flood VOLTOU e com os estáticos em `medium` a origem saturou de novo (load 7.3, self-serve HTTP 000, quase OOM). Religar `security_level=under_attack` nos 20 derrubou de volta (conexões despencam, self-serve 301). LIÇÃO: enquanto durar o ataque, os 20 estáticos precisam ficar em **Under Attack**; `medium` só quando o ataque realmente cessar. O rotador (CF Pro + Super Bot Fight) aguenta sem Under Attack. Trade-off aceito: desafio de 5s nos estáticos de SEO é melhor que a rede inteira cair.

**Mitigação de flood (Cloudflare, conta 1)** — usada durante o pico: só o **Under Attack Mode** (desafio JS) segurou — nas 20 zonas ele derruba as conexões de 2000→~10 na origem. `security_level=high` + Bot Fight (grátis) NÃO basta: o botnet fura (voltou a 9000+ conexões). WAF custom criado nas zonas bloqueando a assinatura (UAs curl/SemrushBot/Baiduspider/Chrome150 + IPs) — ajuda mas não substitui o Under Attack. Trade-off: Under Attack mete desafio de 5s em todo visitante real (ruim p/ SEO) — deixar ligado só enquanto durar o ataque.

**Fix definitivo do rotador (FEITO 2026-07-25)**: `cliquex.click` está no **Cloudflare conta 1**, zona `3b4b5ac0afc33d9c803ef68139901edf`, **`active` no plano Pro Website**. NS: `paige.ns.cloudflare.com` / `tanner.ns.cloudflare.com`. A apex+www proxied → 45.142.141.184, SSL **strict** (origem tem cert LE próprio p/ cliquex.click, val. out/2026), rocket_loader off. Postura de segurança do rotador (todas ativas):
- **Super Bot Fight Mode** (Pro): definitely_automated=**block**, verified_bots=**block**. IMPORTANTE: o usuário quer o rotador SEM NENHUM bot (nem Googlebot/mecanismos de busca) — é ferramenta privada, foco em velocidade e zero interferência externa. Por isso verified_bots=block (não allow). Obs: "likely_automated" NÃO existe no Pro (só Business/Ent) → setá-lo dá 10400 Bad Request.
- **WAF custom "bloqueio total de bots"**: block se `cf.client.bot` OU UA vazio OU `lower(http.user_agent)` contém bot/crawl/spider/curl/wget/python/headless/ahrefs/semrush/yandex/baidu/bytespider/axios/etc OU IP atacante. Verificado: Googlebot e curl → 403; navegador real → 302. `0rtt` ligado p/ velocidade.
- **Rate limiting** (phase `http_ratelimit`, não `http_request_ratelimit`): 100 req/60s por IP → managed_challenge, mitigation 600s.
- **WAF gerenciado** da Cloudflare (phase `http_request_firewall_managed`, ruleset id `efb7b8c949ac4650a09736fc376e9aee`).

**SLOWLORIS FALSO-ALARME + FIX (2026-08-19 20:54):** bot cliquex_monitor_bot alertou "4318 conexões :443, possível slowloris sem IP dominante, auto-bloqueio não achou culpado". Investigado na origem certa (`ssh hostinger-vps-srv1166087`, 31.97.173.40). **Não era ataque direto**: ao olhar já tinha caído p/ ~786→628; TODOS os IPs de origem eram Cloudflare (162.158.x/172.71.x/172.68.x/198.41.x), SYN_RECV=1, sem IP atacante — por isso "sem culpado" (tráfego chega todo pela CF, IP real vai no header; banir CF derruba o site). **Gap real corrigido** no `/etc/nginx/nginx.conf`: `client_header_timeout` e `client_body_timeout` estavam em **180s** (exatamente o que o slowloris explora — segura conexão pingando bytes lentos) → baixados p/ **15s (header)** e **30s (body)**; `worker_connections` **1024→4096** (8 CPUs = 32.768 de capacidade, 4× folga; a migração pro Hostinger tinha perdido o tuning antigo de 8192). worker_rlimit_nofile já era 65535 (ok). cliquex.conf tem o guard CF-only (`if $cf_trusted=0 return 403`) — bypass direto barrado; o timeout curto mata slowloris tanto via CF quanto direto na origem. Backup em `nginx.conf.bak-slowloris-*`, `nginx -t` ok, reload sem downtime. Verificado: cliquex.click 302 (edge), /clk 307 (origem). **Regra**: timeouts curtos de header são a defesa nº1 contra slowloris; num servidor atrás da CF, contagem de conexões alta ≠ ataque (é pool de keepalive da CF) — olhar se há IP não-CF dominante antes de alarmar.
